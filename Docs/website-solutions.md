# مقترحات حلول مشاكل الموقع

هذا الملف يترجم المشاكل الموثقة في `Docs/website-issues.md` إلى حلول تنفيذية مقترحة. يفضل تنفيذ الحلول بالترتيب، لأن بعض البنود تعتمد على إصلاحات البنية والمصادقة أولاً.

## 1. إصلاح بناء الإنتاج والنشر

**المشكلة:** أمر `npm run build` يستدعي `scripts/build-vercel.mjs` غير الموجود.

**الحل المقترح:**

1. تحديد منصة النشر المستهدفة وطريقة تشغيل TanStack Start عليها.
2. إما إنشاء `scripts/build-vercel.mjs` ليجهز مخرجات النشر المطلوبة، أو حذف الجزء غير المستخدم من أمر البناء.
3. إضافة فحص بناء إلى CI حتى لا يتم دمج تغييرات تكسر الإنتاج.
4. تشغيل البناء في بيئة نظيفة باستخدام Node.js 22 أو أحدث.

**معيار النجاح:** ينجح `npm run build` من أول مرة بعد `npm install`، وتعمل النسخة الناتجة على منصة النشر.

## 2. تنفيذ صفحة إنشاء المطعم

**المشكلة:** `/setup` صفحة تجريبية ولا تنشئ مطعماً.

**الحل المقترح:**

1. إنشاء نموذج يحتوي على اسم المطعم، الشعار الاختياري، والبيانات الأساسية المطلوبة.
2. إضافة وظيفة خادم مثل `createRestaurant` تتحقق من جلسة المستخدم على الخادم.
3. إنشاء سجل المطعم مع `owner_id` للمستخدم الحالي.
4. إنشاء الدور الأساسي `admin` في عملية واحدة أو مع معالجة تمنع إنشاء سجل ناقص.
5. بعد النجاح، إعادة التوجيه إلى `/dashboard` مع تحديث بيانات المطعم.
6. منع المستخدم المصادق الذي لا يملك مطعماً من استخدام fallback المعاينة.

**معيار النجاح:** المستخدم الجديد ينتقل من التسجيل إلى الإعداد، ينشئ مطعماً، ثم يرى مطعمه الحقيقي بعد إعادة تحميل الصفحة.

## 3. تنفيذ استعادة كلمة المرور

**المشكلة:** `/forgot-password` لا يرسل رسالة استعادة.

**الحل المقترح:**

1. إضافة حقل بريد إلكتروني مع تحقق من الصيغة.
2. استدعاء `sendPasswordResetEmail` من طبقة المصادقة المستخدمة فعلياً.
3. إظهار رسالة عامة موحدة بعد الإرسال حتى لا يتم كشف وجود البريد في النظام.
4. إنشاء صفحة أو حالة لتعيين كلمة مرور جديدة بعد فتح رابط البريد.
5. التحقق من صلاحية رمز الاستعادة وانتهائه قبل السماح بالحفظ.

**معيار النجاح:** يستطيع المستخدم طلب رابط، فتحه، تغيير كلمة المرور، ثم تسجيل الدخول بالكلمة الجديدة.

## 4. استبدال وظائف الخادم الوهمية

**المشكلة:** وظائف الإعدادات والموظفين وTelegram والملخصات والتنبيهات تعيد بيانات ثابتة.

**الحل المقترح العام:**

1. إضافة طبقة تحقق مشتركة للجلسة الحالية والمطعم المرتبط بها.
2. التحقق من صلاحية الدور قبل كل عملية كتابة أو قراءة.
3. تنفيذ عمليات Firebase الفعلية داخل server functions، وليس من الواجهة مباشرة عند الحاجة إلى أسرار أو صلاحيات خاصة.
4. إعادة نتيجة موحدة مثل `{ data, error }` أو رمي خطأ واضح عند الفشل.
5. تحديث الواجهة لتعرض حالات التحميل والنجاح والفشل بناءً على النتيجة الحقيقية.

**حسب المجال:**

- **الإعدادات:** حفظ بيانات المطعم والـ splash والثيم في مجموعة المطعم.
- **حسابات الموظفين:** إنشاء الحسابات وتحديثها وحذفها مع التحقق من أن المنفذ مالك أو مدير مخول.
- **Telegram:** حفظ رمز البوت مشفراً أو في تخزين خادمي محمي، والتحقق من الرمز قبل تفعيله.
- **الملخصات اليومية:** حفظ الوقت والتفعيل، وتشغيل مهمة مجدولة منفصلة للإرسال.
- **تنبيهات المخزون والمشتريات:** إنشاء خدمة إرسال مركزية وتسجيل نتيجة كل عملية.

**معيار النجاح:** بعد تنفيذ أي عملية ثم إعادة تحميل الصفحة، تظهر البيانات المحفوظة فعلياً، وتظهر رسالة خطأ عند فشل الخدمة.

## 5. نقل rate limiting إلى الخادم

**المشكلة:** الحماية الحالية تعتمد على `localStorage` ويمكن تجاوزها.

**الحل المقترح:**

1. إبقاء المحدد المحلي لتقليل الطلبات غير الضرورية وتحسين تجربة المستخدم فقط.
2. إضافة rate limiter خادمي مرتبط بالبريد الإلكتروني وعنوان الشبكة أو معرف جلسة مناسب.
3. تخزين العدادات في خدمة مشتركة أو قاعدة بيانات، وليس في ذاكرة المتصفح.
4. جعل رسائل الخطأ عامة وعدم كشف تفاصيل غير ضرورية عن الحسابات.
5. تطبيق نفس الحماية على تسجيل الدخول، التسجيل، إعادة تعيين كلمة المرور، والتحقق من PIN للأدوار.

**معيار النجاح:** حذف بيانات المتصفح أو استخدام جهاز آخر لا يلغي الحماية الخادمية.

## 6. حسم طبقة Backend والتوافق مع Supabase

**المشكلة:** التطبيق لا يستخدم Firebase بصيغة أصلية بالكامل؛ الواجهة تستورد عميلاً باسم `supabase`، لكنه في الحقيقة يعيد تصدير محول Firebase.

**الحل المقترح:**

1. اعتماد قرار معماري واضح: Firebase هو Backend الوحيد، أو العودة إلى Supabase الفعلي؛ عدم إبقاء التسمية المختلطة كحل دائم.
2. إذا تم اعتماد Firebase، تغيير اسم طبقة التوافق تدريجياً إلى `firebaseClient` أو repositories typed، مع تحديث الواردات حسب المجالات.
3. توثيق العمليات التي يدعمها المحول فقط، ومنع إضافة استدعاءات Supabase جديدة إلى الواجهة.
4. إبقاء طبقة توافق مؤقتة فقط أثناء الانتقال، مع خطة لإزالتها بعد نقل الوحدات.

**معيار النجاح:** يعرف كل مطور ومكوّن بوضوح أن Firebase هو المصدر الفعلي للبيانات، ولا توجد افتراضات غير صحيحة عن وجود Supabase.

## 7. إعادة تصميم محول Firebase المتوافق مع Supabase

**المشكلة:** المحول يعتمد على Proxy و`any`، وبعض العمليات لا تطابق سلوك الاستعلام الحقيقي.

**الحل المقترح:**

1. تحديد مجموعة العمليات التي يستخدمها التطبيق فعلياً في واجهة typed واضحة.
2. استبدال Proxy العام بعمليات صغيرة ومحددة لكل مجال أو repository.
3. تنفيذ `like` و`ilike` بطريقة مدعومة فعلياً، أو منع استخدامها وإضافة بحث مناسب في Firestore.
4. عدم إعادة نجاح وهمي للعمليات غير المدعومة؛ إرجاع خطأ واضح يساعد على اكتشاف الخلل.
5. فصل عميل preview عن عميل Firebase الحقيقي حتى لا تختلط دلالات البيانات.
6. إضافة اختبارات للاستعلامات الأساسية: `eq`, `in`, `order`, `limit`, `insert`, `update`, و`delete`.

**معيار النجاح:** تكون نتائج preview المعلنة متوافقة مع سلوك الإنتاج، وتفشل العمليات غير المدعومة بشكل صريح.

## 8. تنفيذ OAuth وRealtime في Firebase

> **ملاحظة القرار:** أُزيل تسجيل الدخول الاجتماعي (Google وApple) بالكامل من التطبيق، وبقي تسجيل الدخول بالبريد وكلمة المرور فقط. لذلك لا يُنفَّذ هذا الحل، ويقتصر النطاق على Realtime في حال الحاجة إليه.

**المشكلة:** `signInWithOAuth` و`channel()` في المحول الحالي دوال وهمية.

**الحل المقترح:**

1. تنفيذ Google وApple عبر Firebase Auth providers باستخدام `signInWithPopup` أو `signInWithRedirect`.
2. توحيد نتيجة OAuth مع واجهة `auth` الحالية، وإرجاع المستخدم والجلسة الفعلية.
3. استبدال `channel().subscribe()` باشتراكات Firestore `onSnapshot` للمجموعات التي تحتاج تحديثاً فورياً.
4. تنظيف الاشتراك عند مغادرة المكوّن، ومعالجة حالات الاتصال والانقطاع.
5. إذا لم تكن الشاشة بحاجة إلى Realtime، استخدام polling محدود ومعلن بدلاً من اشتراك وهمي.

**معيار النجاح:** تسجيل الدخول الاجتماعي ينشئ جلسة حقيقية، وتصل تغييرات الطلبات إلى الشاشات دون إعادة تحميل عندما تكون Realtime مفعلة.

## 9. إكمال وظائف الأدوار والتوصيل والاستلام

**المشكلة:** بعض وظائف النادل والكاشير والطاهي والتوصيل والاستلام ما زالت placeholders.

**الحل المقترح:**

1. إعداد جدول مراجعة يربط كل `createServerFn` بعملية Firebase المطلوبة.
2. تنفيذ القراءة والكتابة الفعلية للقوائم، التفعيل، PIN، الطلبات، وحالات التوصيل.
3. إضافة تحقق موحد من الجلسة والدور و`restaurantId` قبل كل عملية.
4. إعادة أخطاء صريحة عند عدم توفر Backend أو فشل العملية بدلاً من `[]` أو `{ ok: true }` ثابتة.
5. اختبار كل دور من تسجيل الدخول حتى تنفيذ عملية وتحققها بعد إعادة التحميل.

**معيار النجاح:** لا توجد وظيفة مستخدمة من واجهة إنتاجية تعيد بيانات ثابتة أو نجاحاً وهمياً.

## 10. تقليل استخدام `any`

**المشكلة:** طبقة البيانات تحتوي على أنواع عامة كثيرة تخفي الأخطاء.

**الحل المقترح:**

1. تعريف أنواع للكيانات الرئيسية مثل المطعم، الطلب، الموظف، الدور، المنتج، والإعدادات.
2. تعريف نوع موحد لنتائج القراءة والكتابة والأخطاء.
3. استبدال `any` تدريجياً في طبقة المصادقة والعمليات الحساسة أولاً.
4. تفعيل فحص TypeScript ضمن CI باستخدام `tsc --noEmit` إذا لم يكن البناء يغطيه.
5. استخدام `unknown` في حدود البيانات الخارجية مع تحويل محقق بدلاً من `any`.

**معيار النجاح:** يكتشف TypeScript أسماء الحقول الخاطئة وأنواع المدخلات غير الصحيحة قبل التشغيل.

## 11. تقليل استخدام `any`

**الحل المقترح:**

## 12. فصل preview عن المستخدمين الحقيقيين

**المشكلة:** المستخدم المصادق بلا مطعم قد يرى `مطعم السهل` الوهمي.

**الحل المقترح:**

1. تحديد وضع المعاينة بعلامة صريحة مثل query parameter أو session demo موثقة.
2. السماح بالبيانات الوهمية فقط عندما لا توجد جلسة حقيقية أو عندما يطلب المستخدم وضع المعاينة صراحة.
3. عند وجود جلسة حقيقية بلا مطعم، إعادة التوجيه إلى `/setup` بدلاً من إنشاء `mock-restaurant-id`.
4. إضافة حارس مركزي يمنع عمليات الكتابة الوهمية من الوصول إلى بيانات الإنتاج.
5. إظهار شارة واضحة في كل شاشة preview.

**معيار النجاح:** لا يرى المستخدم المصادق بيانات المطعم الوهمي، ولا يمكن لبيانات preview تعديل بيانات Firebase الحقيقية.

## 13. إكمال الترجمة

**المشكلة:** الفرنسية والإنجليزية معلنتان لكن الموارد المتاحة عربية فقط، مع وجود نصوص صلبة داخل الصفحات.

**الحل المقترح:**

1. اختيار اللغات التي سيتم دعمها فعلياً في الإصدار الحالي.
2. إذا كان الدعم العربي فقط، إزالة `fr` و`en` مؤقتاً من `supportedLngs`.
3. إذا كان الدعم متعدد اللغات مطلوباً، إنشاء ملفات موارد كاملة لكل لغة.
4. نقل رسائل التحقق والأخطاء والعناوين والنصوص الموجودة داخل JSX إلى مفاتيح i18n.
5. اختبار اتجاه الصفحة، تنسيق الأرقام، العملة، وأزرار التنقل لكل لغة.

**معيار النجاح:** لا تظهر مفاتيح ترجمة أو نصوص عربية عند اختيار لغة أخرى، ويظل اتجاه RTL مضبوطاً للعربية.

## 14. إصلاح OAuth callback

> **ملاحظة القرار:** أُزيل تسجيل الدخول الاجتماعي (Google وApple) بالكامل، لذا لم يعد هناك مسار `auth/callback` ولا حاجة لهذا الحل.

**المشكلة:** الواجهة تستخدم `/auth/callback` دون وجود route ظاهر لمعالجة callback.

**الحل المقترح:**

1. تحديد ما إذا كان Firebase أو مزود مصادقة آخر هو المسؤول النهائي عن OAuth.
2. إنشاء مسار callback فعلي إذا كانت المنصة تحتاجه.
3. معالجة الجلسة أو رمز OAuth ثم استدعاء `getPostAuthRedirect`.
4. إضافة حالة تحميل وخطأ واضحة، وعدم وضع رمز المصادقة في query string أكثر من اللازم.
5. تسجيل redirect URI الصحيح في إعدادات Google وApple وبيئة الإنتاج.

**معيار النجاح:** تسجيل الدخول عبر Google وApple ينتهي إلى `/dashboard` أو `/setup` حسب حالة الحساب دون 404 أو جلسة مفقودة.

## 15. تأمين رموز preview

**المشكلة:** الرموز `mock_waiter` و`mock_chef` و`mock_cashier` ثابتة وقابلة للتوقع.

**الحل المقترح:**

1. جعل الرموز الوهمية غير صالحة خارج وضع المعاينة المحلي.
2. عدم إرسالها إلى خدمة المصادقة أو تخزينها كرموز حقيقية.
3. إضافة تحقق بيئي يمنع `mock_*` في production.
4. استخدام رمز عشوائي مؤقت عند الحاجة لمحاكاة جلسة preview.
5. إبقاء كل بيانات preview منفصلة عن مجموعات الإنتاج.

**معيار النجاح:** لا يمكن استخدام رمز preview للوصول إلى شاشة أو بيانات حقيقية في بيئة الإنتاج.

## 16. منع رسائل النجاح الوهمية

**المشكلة:** إعدادات Telegram والملخصات قد تعرض نجاحاً رغم عدم تنفيذ العملية.

**الحل المقترح:**

1. تعديل server functions لتعيد نتيجة العملية الفعلية.
2. عدم عرض toast نجاح إلا بعد استلام نتيجة حفظ مؤكدة.
3. عرض رسالة فشل مع إمكانية إعادة المحاولة عند تعذر الخدمة.
4. إعادة قراءة الحالة من الخادم بعد الحفظ للتحقق من الثبات.
5. عدم إعادة رموز البوت الحساسة في response أو تخزينها في `localStorage`.

**معيار النجاح:** تتطابق الرسالة التي يراها المستخدم مع الحالة الفعلية بعد إعادة تحميل الصفحة.

## خطة تنفيذ عملية

### المرحلة الأولى: منع فشل النشر

- إصلاح `npm run build`.
- تشغيل lint وTypeScript والبناء في بيئة نظيفة.
- إضافة فحص تلقائي للبناء في CI.

### المرحلة الثانية: إكمال دورة الحساب

- تنفيذ `/setup`.
- تنفيذ `/forgot-password`.
- منع المستخدم المصادق من fallback المعاينة.
- إزالة تسجيل الدخول الاجتماعي (Google وApple) بالكامل.

### المرحلة الثالثة: ربط الوظائف بالبيانات الحقيقية

- تنفيذ repositories أو server functions typed.
- تنفيذ الإعدادات والموظفين.
- تنفيذ Telegram والملخصات والتنبيهات.
- إضافة صلاحيات الملكية والأدوار.

### المرحلة الرابعة: تحسين الأمان والجودة

- نقل rate limiting إلى الخادم.
- فصل preview عن production.
- تقليل `any`.
- إضافة اختبارات تكامل للاستعلامات والعمليات الحساسة.

### المرحلة الخامسة: الترجمة وتجربة الاستخدام

- إكمال موارد اللغات أو تقليص اللغات المدعومة.
- نقل النصوص الصلبة إلى i18n.
- اختبار RTL والاستجابة على الهاتف وسلوك رسائل الخطأ والنجاح.
